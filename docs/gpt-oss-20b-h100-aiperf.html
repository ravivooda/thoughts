01 / FINDINGS

What changed under load

The GPU reached high aggregate throughput well before the serving system reached a good operating point for users.

01

Throughput plateaued

Short-context throughput flattened between concurrency 400 and 1,600, peaking at 800 before declining.

02

KV pressure appeared as queueing

At saturation, fewer requests stayed resident while waiting queues and time to first token rose sharply.

03

Half KV moved the boundary

With 28.26 GiB, KV reached 100% at concurrency 800 instead of 1,600 under the auto-sized policy.

04

Raw throughput hid the damage

Aggregate output stayed near 8K tokens/s while average TTFT at concurrency 800 rose from 10.0s to 18.3s.

KV cache is primarily a capacity resource. Reducing it did not make token generation faster; it reduced the number of requests vLLM could keep resident.

04 / CAPACITY

The caller sees a different curve

Dividing server-wide output throughput by configured concurrency provides a simple fair-share estimate. It falls rapidly after the useful operating range.

Estimated output rate per configured caller

OUTPUT TOKENS / SECOND / CALLER

Estimate = aggregate output token throughput ÷ configured concurrency. Waiting callers receive no tokens, so this is capacity intuition rather than an individual streaming trace.

For the auto-KV stress run, concurrency 200 delivered about 38.1 fair-share tokens/s. Raising concurrency to 400 added only 3.4% aggregate output throughput, but reduced fair share to 19.7 tokens/s and increased average TTFT by 86%.

05 / DECISIONS

Serving recommendations

Optimize for latency-constrained goodput and queue depth, not the single highest tokens-per-second number.

Default range

Start long-context capacity planning around concurrency 200–400 on this hardware and workload, then tune against an explicit TTFT objective.

KV sizing

Use automatic profiling or a conservative explicit --kv-cache-memory-bytes value. A forced 62.05 GiB allocation failed at startup with CUDA OOM.

Admission

Apply request admission control before KV reaches 100%. Queue depth and waiting requests are leading capacity signals.

Benchmarking

Use sustained, duration-bounded workloads with realistic input/output distributions and evaluate TTFT, ITL, and SLO goodput alongside throughput.

Caller metric

Do not interpret aggregate output tokens/s as the stream rate seen by every caller. Track per-request latency distributions in production.

vLLM uses continuous batching. Here, “concurrency” is the number of in-flight AIPerf requests, while max-num-seqs is a scheduler cap—not a promise that every request is resident on the GPU at once. Under half-KV pressure, roughly 450–500 requests were running while the remainder waited.

The complete benchmark matrix, machine-readable results, and runner scripts are available in the experiment directory.

Notes and limitations
  1. Results represent one H100, one model build, and the software versions shown. They should not be generalized without rerunning on the target stack.
  2. Short-context runs were request-count bounded and more sensitive to warm state and run variance than the sustained stress profiles.
  3. The high-memory short-context run at concurrency 1,600 produced an invalid outlier and was excluded from capacity conclusions.
  4. Fair-share tokens/s is aggregate throughput divided by configured concurrency. It is not a direct per-user streaming measurement.
